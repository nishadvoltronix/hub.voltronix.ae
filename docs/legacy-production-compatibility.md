## Why activation remains blocked

The native runtime verifies its own exact table inventory, migration ledger, server identity, runtime grants and selected constraints before serving database operations. It assumes its own coordination, sessions, audits and schema. These checks must remain intact. Creating native tables, adding a ledger, changing passwords or running native migrations in the PHP database is not a compatibility solution.

Even a read-only historical screen requires trustworthy relationship and permission mappings; broad access cannot be granted merely because a legacy row exists. A future architecture may use a separately approved Hub-owned store for sessions/audits and a strictly read-only legacy adapter, but that design and its complete authorization/consistency contract are not implemented here. Supporting write operations while both applications run needs additional evidence and testing. The unchanged-legacy-database requirement remains binding.

Without compatible persistence, login/session creation, dashboards, CRM records, settings, permission changes, saved quotations/PDFs, jobs, history and protected downloads cannot be accepted as functional production workflows. Zoho-dependent actions and synchronization remain disabled separately; supplying OAuth credentials would not resolve database compatibility.

## Required evidence before adapter work can be completed

Obtain these as approved offline artifacts through a separately authorized process; no server connection is part of this task:

1. The deployed PHP revision and enabled route/configuration behavior, with secrets removed, plus authoritative complete DDL and database product/version. Include all column definitions, keys, indexes, foreign keys, defaults, collations, generated columns, views, triggers, routines, events and SQL modes. Record capture time, provenance and checksums. Metadata visibility must be demonstrably complete.
2. Sanitized representative relational fixtures with counts and a documented capture boundary: local/external identity mapping, duplicate/orphan diagnostics, status/department/permission domains, timestamp/timezone conventions and decimal/currency fields. Preserve problematic historical cases; do not manufacture clean foreign keys.
3. Aggregate password-format evidence and a test account fixture for each supported algorithm, including inactive users and grant revocation. Never publish hashes, real credentials, private user exports or production sessions.
4. Historical quotation fixtures with original persisted values, revisions, line order, discounts, taxes, adjustment, currency and PDF expectations; explicit business decisions for ambiguous semantics. New percentage-only calculations do not establish historical equivalence.
5. A privately retained attachment manifest and offline originals with hashes, owning task/log/user relationships, allowed storage roots and permission decisions. Preserve missing/rejected originals with counted reasons.
6. Ownership of Zoho schedules/webhooks and field writes, remote identity mapping, retries/idempotency/reconciliation and a verified isolated test environment. Keep a second sync writer disabled.
7. Isolated-restoration acceptance for both actual applications, including concurrent edits, duplicate numbering, permission/password changes, denied file access, failures and recovery. Verify the legacy schema/records/files remain unchanged for read-only use; any future write proposal needs explicit scope and guarantees. Test rollback without restoring over ongoing PHP writes.
